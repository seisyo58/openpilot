# 通常要求・協調制動・保持・解除の観測分類

2026-11-05。接続経路の調査 `05bb978283` に続く、既存NPZのオフライン解析。実車への接続・送信・試験予約・制御変更はない。

## 得られたこと

3走行から、停止保持候補を13区間抽出した。解除を観測できた12例は、受信RESを伴う9例、装置CANCEL要求を伴う3例に分かれる。欠損に接する1区間は解除未観測として残した。

両端を1秒ずつ除く中央部が取れた12区間・計17,996サンプルは、すべて次の組み合わせだった。

- 2B0有効bit = 0
- 1C3数値 = 0、byte5 bit2 = 1
- 1CB byte4 bit0 = 1、byte5 bit2 = 1

これは保持中の受信波形を記述する組み合わせであり、これらを送れば保持できるという条件ではない。短い残り1区間は両端1秒を除くとデータがなく、この中央部評価に含めない。

## 1. 分類方法

[classify_events.py](../classify_events.py)を作成し、[監査JSON](../evidence/leaf_event_classification_20261105.json)に集計・制動候補区間・保持区間・解除前後の履歴を保存した。入力のSHA256も含む。

基準はbus1の1C3受信フレーム。2B0と1CBは直前30ms以内、30Fは直前150ms以内、carStateは直前100ms以内の値だけを使う。先のサンプルを遡って適用しない。欠損や古い値が一つでもあれば `unknown_stale` に分ける。

|分類|観測上の定義|
|---|---|
|通常要求候補|ACC有効、ペダル非操作、30F保持候補OFF、2B0有効・通常パターン、1C3数値0|
|協調制動候補|上記のACC・ペダル・保持条件に加え、車速0.1m/s超、2B0有効・特別パターン、1C3数値正|
|停止保持候補|車速0.1m/s以下かつ30F byte0 bit4 ON。他の候補bitや数値の一致を条件にしない|
|その他の観測組み合わせ|鮮度は十分だが上記に属さない。ペダル操作、ACC OFF、遷移途中等を含む|
|鮮度不足|必要な直前サンプルがない、または許容時間より古い|

2B0の特別パターンは `a8 27 d5 ac 5b 00 ?e 09` と照合し、byte6の上位カウンターnibbleだけを無視する。旧数値化式の「2518」を物理値のしきい値として使わない。通常値の最新候補式と特別パターンの照合は分離した。

停止保持候補では、1C3数値や1CB候補bitを条件に入れず、それらの一致・不一致を結果として集計する。これにより「条件に含めたbitが全例で一致した」という循環を避ける。車速と30Fも独立した保持力測定ではない。

合計は各入力の1C3受信数86,888 / 63,322 / 200,812に一致する。連続サンプルは独立試行ではない。

協調制動候補の連続区間は6 / 3 / 55。そのうち最初と最後の観測点が100ms以上離れる区間は4 / 2 / 42で、JSONへ時刻・速度・1C3ピーク値を保存した。30ms超の受信間隔で必ず区切り、短い不一致を平滑化してつながない。以前の[協調制動の回帰](leaf_braking_coordination_findings.md)は速度・境界除外等の条件が異なるため、区間数や採用点数を直接比較しない。

「その他」を任意の新モードへ割り当てない。例えば2B0通常有効なのに1C3数値が正の点は59で4点、5aで2点、5cで47点ある。CANの更新周期や過渡の影響を含み、純粋な通常→制動の二状態だけでは受信時系列を漏れなく表せない。

送信側は `sendcan` 由来の要求記録。受信RESを含むフレームをホストがそのまま送る場合もあり、TXにRESがあるだけでホストが独自にRESを生成したとはいえない。CAN上の送信完了・受信ECUの受理・その操作が解除の原因であることも、この表だけでは確定しない。

59の別ファイル `route59_tx.npz` を併用した。5a/5cは各抽出NPZ内の `tx_b2_239`。carControlはこれらのNPZにはなく、今回新たに再監査していない。[5cでの既存のcarControl照合](leaf_2022_model_and_cancel_findings.md)を別の証拠として区別する。

### 短い窓では操作の出所を取り違える

5cの537.995秒OFFの直前0.5秒では受信RESは0、送信要求RESは3フレーム。一見するとホストだけの操作に見える。しかし受信RESは約880～759ms前に7フレームあり、その時期の送信要求にもRESがある。受信側の操作に続いて送信側にも後続のRESが見える例として扱い、純粋な自動発進の独立例には数えない。

そのためJSONでは直近 `[-0.5,+0.7]秒` と履歴を含む `[-3.5,+0.7]秒` を両方残す。広い窓内にあるだけの操作を原因と断定せず、先頭オフセットも保存する。

### アクセル入力とCANCELが重なる59の例

464.756秒OFFに対し、gasPressed立ち上がりは約77.7ms前、最初の送信要求CANCELは約56.4ms前、2B0有効化は約9.3ms前。その後1CB候補が約31.3ms、1C3 bit2が約49.9msで落ちる。受信CANCEL・RESは前記窓でともに0。

従って「2B0が有効になり保持候補が落ちた」という形だけをRES経路と同一視できない。アクセルと装置CANCELが重なる別の文脈として分ける。装置要求を除いた純正アクセル解除の挙動は、この例では評価できない。

## 3. 次のモデルへ渡せる知識と境界

- 通常要求と協調制動は、2B0の通常/特別パターンと1C3数値の組み合わせで観測分類できる。ただし切り替えを生む目標減速度・有効化手順は不明。
- 保持には「数値0でもbitが残る」安定した受信シグネチャがある。数値だけを0へ戻すモデルでは観測を表せない。
- 解除は一つの列へまとめず、受信RESあり、ペダル＋装置CANCEL、欠損による不明に分ける。CANCELがないことも、純正だけの挙動の証明ではない。
- 正常な受信パターン、車両が受け入れる指令、物理制動の結果を区別する。これらの分類をそのまま制御状態機械へ組み込まない。

次の解析に使える候補区間一覧が揃った。送信側モデルを進めるには、各受信シグネチャが要求か応答か、純正送信をどう引き継ぐかという[接続経路の未解決点](leaf_transport_paths_20261105.md)が引き続き残る。

## 再現と検証

```sh
.venv/bin/python -m openpilot.tools.leaf_research.classify_events \
  /path/to/work/acc_frames.npz \
  /path/to/work/route5a_frames.npz \
  /path/to/work/route5c_frames.npz \
  --tx-59 /path/to/work/route59_tx.npz \
  --out /tmp/leaf-event-classification.json

.venv/bin/python -m unittest discover -s openpilot/tools/leaf_research/tests
```

出力は既存ファイルを上書きしない。テストでは未来値の誤利用、欠損を跨ぐ区間結合、特別パターンの誤一致、未観測解除の捏造、短い窓によるRES履歴の取りこぼしを検査する。

元NPZの再集計であり、原rlogからの再抽出ではない。Event時刻はCANをまとめた記録なので、数msの差をECU内部の因果順序や固定待ち時間の根拠にしない。既存データに合わせて作った記述分類で、未知ログに対する独立した精度評価ではない。
