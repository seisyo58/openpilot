# 停止保持と解放のCAN経路

追記：停止中ブレーキによる解除の2例には装置のCANCEL送信要求が介在していた。純正ブレーキ操作だけの解除とは扱わない。また1181秒付近の停止中有効化は公式の操作条件との相違が残る。訂正と根拠は leaf_2022_model_and_cancel_findings.md を参照。


ルート5cの7保持区間について、開始前後・解除前後の全CANを再抽出した。対象はbus/address 91組、508,303フレーム。数値だけでなく全データbitを比較し、解除前後で安定して変わる候補を選んだ。byteは0始まり、bitはbyte内LSBを0とする。候補選択は同じ7例に基づく探索であり、独立した予測検証ではない。

## 最も重要な訂正

1C3の制動数値はゼロでも、byte5 bit2は保持中ONだった。従って「2B0非有効・1C3数値ゼロだから、要求を送らず車両側だけで保持している」という解釈は成り立たない。以前のレポートでいう「1C3正の要求ゼロ」は数値フィールドについての事実であり、メッセージ全体の非有効を意味しない。

安定した保持中の1C3は例えば `000000006404ff2b`。bit2=1、数値0、byte5 bit7=0。bit2が落ちた例は `000000006400ff27`。下位2bitはカウンターなので、単純なbyte値比較ではなくbitを分離した。

bit2は走行中の制動でも立つため、停止保持専用bitとは断定できない。保持要求、制動制御の状態、応答の反映などが候補として残る。

## 保持中に残るもの

5cの全7区間で、開始1秒後～最後のONフレーム1秒前の安定区間では以下が続いた。

- 1C3 byte5 bit2 = 1
- bus0の1CB byte4 bit0 = 1
- bus0の1CB byte5 bit2 = 1
- 2B0の有効bit = 0
- 1C3の制動数値 = 0

1CBの2bitは5c全201,098フレームで一致した。ただし59・5aでは全区間では一致しないため、同義の重複bitと一般化しない。

通常のACC停止6例では、1CB候補bitは保持候補0x30F bit4の立ち上がりから約190～200ms後に立った。ブレーキを踏んだまま停止中ACCを有効にした1例では約290ms後だった。1C3 bit2は通常は走行制動からすでに立っており、この1CB保持候補bitと同じ信号ではない。

## 解除順序

基準時刻は、各区間の実際の0x30F bit4 OFFフレーム。候補選別時の近似時刻ではなく元フレームから再取得した。

|保持開始 秒|解除|2B0有効化 ms|1CB候補OFF ms|1C3 bit2 OFF ms|
|---|---|---:|---:|---:|
|526.515|RES|-9.2|120.6|129.9|
|607.426|RES|-11.1|80.2|89.5|
|705.415|RES|-10.6|39.7|59.3|
|840.145|brake|なし|10.6|21.0|
|1181.126|brake|なし|10.5|30.4|
|1448.666|RES|-9.4|81.1|100.7|
|1586.016|RES|-10.3|39.9|59.7|

RESの5例では、2B0が有効になった後で1CBの保持候補が落ち、さらに約9～20ms後に1C3 bit2が落ちた。運転者のブレーキによる2例では、2B0の有効化を伴わず1CB・1C3の候補が落ちた。1CBの第2の11bit数値は、RESではその後減少し、ブレーキ介入では増加する例がある。保持モードの解除と、実際にブレーキ力がゼロになることは分けて扱う必要がある。

この時間順序は、1C3 bit2が保持解除の最初のきっかけだという仮説には合いにくい。1CBの状態を遅れて反映している可能性もある。ただし送信周期・他の要求の影響があり、観測だけで送信元やECU内部の因果関係は確定できない。

## 追加で見つかった周辺候補

- bus1 2D4 byte0 bit7は、RES5例すべてで2B0有効化と同じ受信時刻に変化。ブレーキ解除2例では変化なし。
- bus1 28F byte2 bit6は、RES5例すべてで0x30F保持候補OFFと同じ受信時刻に変化。ブレーキ解除2例では変化なし。

同じ受信イベントに入った信号の厳密な送信順序は比較できない。これらは再発進・走行許可の周辺候補として優先的に調べる対象だが、親の要求や独立した解放指令とまでは言えない。

## 過去の2ルートでの確認

1C3 bit2は59の保持候補456フレーム中454、5aの279中277、5cの1344中1342でONだった。OFFとのずれは解除付近などを含む。3ルートすべてで、1CB候補bitの下降に近接する1C3 bit2下降が見つかり、1C3が約10～20ms遅れる関係を確認した。

これにより、今回の残留bitはe-Pedal OFFでだけ現れた特殊例ではないと考えられる。一方、1C3 bit2立ち上がりと1CB保持候補立ち上がりは一致せず、どちらも同じ保持指令とみなすことはできない。

## 実装に対する現時点の見解

3秒後の状態を省くこと自体は設計上の選択肢として残る。ただし純正の保持を利用する場合、数値をゼロにするだけの再現では不足する可能性がある。保持中に残る1C3 bit2と、1CBが示す状態を明示的に扱う必要がある。

現状で有望なのは「純正は、数値による制動から、状態bitを伴う保持へ移り、再び走行要求が出ると保持を解除する」という動作像。1C3 bit2を保持すれば自前制御でも保持が成立するか、あるいは単なる応答なので別の要求が必要かは未確定。

試作のbit2を単に『制動数値>0』で決める仮定は、今回の観測された保持状態を再現できない。実車用の規則には採用できない。実車送信は行っていない。
