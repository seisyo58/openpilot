# 追加ハードウェアを最小限にする方針

2026-11-03。ZE1 e+ G（2022年6月、ユーザー申告）、通常のNissan A・配線変更なし。

## 現時点の判断

追加装置の購入・ハーネス改造はまだ進めない。まず、既存のADAS診断機能で純正送信を止め、既存のbus 1接続で引き継ぐ方式の成立条件を調べる。これは同じIDを競合送信する案とは別。対象車で成立・復帰を確認したものではない。

従来の「CANを分離する方式が本命」という判断は、純正送信を止められない場合の代替案へ位置づけを変更する。通常ハーネスの物理的制約は変わらない。

## 既存Pandaだけで両CANを分離できるか

現在の接続は操舵側ネットワークをCAN0/CAN2に分離し、別のネットワークをCAN1で直結のまま観測する構成。独立した2つのネットワークをそれぞれ2分割して同時に中継するなら、論理上4つの独立したCAN接続先が必要となる。現在の構成では3系統しか用いていないため、単にバス番号を設定し直して4つの独立接続先を作ることはできない。

Tresのコードには4つのトランシーバーが現れるが、CAN_MODEの切替では同じ第2CANコントローラーの接続先を選んでいる。4つ目をそのまま独立した第4CANポートとして使えるという意味ではない。

既存の操舵側の分離をやめて縦制御側へCAN0/CAN2を割り当て直す案も、純正操舵要求との競合を再び解く必要がある。そのため追加機器なしの単純な代替案とはしない。まだ車両配線図によるネットワーク接続先・ECU特定は完了していない。

## 追加機器なしの先行実装

StarPilotの現行Nissan実装を再確認した。該当ファイルの最終変更はcfd221b89cec223397f0a805791136aa9b958758。

[一次ソース：Nissan interface.py](https://github.com/StarPilotHQ/StarPilot/blob/cfd221b89cec223397f0a805791136aa9b958758/opendbc_repo/opendbc/car/nissan/interface.py)

コードの設計は次のとおり。

- ADASの診断セッションへ入り、通常送信の停止を要求する。
- bus 1で対象2信号が来なくなり、ほかの通信は残っていることを検査する。
- 成立したときだけホストから駆動・制動候補を送信する。
- 復帰時は通常セッションへ戻し、対象通信の再開を検査する。

ただし機能フラグは現在もFalse。特定の2025 SV PlusのファームウェアとNISSAN_LEAFを対象とする条件もある。存在する実装は検証材料であり、2022年IC仕様での実用成功の証拠ではない。

## 今回の車両との照合

59と5cの既存rlogに保存されたcarParamsを読み直した。追加の診断通信は送っていない。

- 認識車種は両方ともNISSAN_LEAF_IC。
- 診断アドレス0x707の記録済みファームウェアは両ログで一致。識別文字列先頭は6WK6ADB。
- 先行実装の2025年車の条件は先頭6WK2CDBを含む別の完全バイト列。
- したがって、機能フラグがFalseであることに加え、車種・ファームウェア条件もそのままでは一致しない。
- 同じ応答情報がbus 0/1に記録されているが、これだけで物理ECUが2台あることやゲートウェイ構成までは断定しない。

照合の詳細はleaf_recorded_adas_firmware.json。

## 先行方式で未解決の点

1. 診断による通常送信停止が対象2信号以外に何を止めるか。AEB、操舵、状態通知への影響は未確認。
2. 復帰判定は先行コードでは対象2信号のどちらかが来れば成功する。両方の継続復帰、周期・カウンターの連続性、受信側の状態までは保証しない。
3. アプリ停止・通信断・電源断時に、診断セッションと要求がどう戻るか。通常のdeinitが呼ばれることを前提にできない。
4. CAN1上の他の通信が見えて対象が短時間見えないだけでは、ECU全体の健全性や復帰可能性までは確認できない。
5. 2022年車の診断セッション仕様と送信停止の副作用、確実な復帰条件。通常のファームウェア取得に応答した事実からは推定できない。

これらが確認できれば、追加インターフェースなしの方式を検討する根拠になる。確認できなければ、物理中継方式とそのための最小限の追加ハードウェアに戻る。

## 次に進める調査

対象ADAS型番に対応する診断・整備資料と既存の検証報告を探し、停止対象と復帰仕様を確認する。現時点では配線変更・購入・診断による送信停止・実車への要求送信は行っていない。次の実車試験をするなら、いきなり駆動させるのでなく、影響範囲と確実な復帰を確認できる設計が先に必要。
