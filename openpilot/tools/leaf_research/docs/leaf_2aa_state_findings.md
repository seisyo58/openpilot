# 2AAの複合状態値と、受信ログ解析で残る限界

追記：停止中ブレーキによる解除の2例には装置のCANCEL送信要求が介在していた。純正ブレーキ操作だけの解除とは扱わない。また1181秒付近の停止中有効化は公式の操作条件との相違が残る。訂正と根拠は leaf_2022_model_and_cancel_findings.md を参照。


3ルートの2AAについて、先頭word下位5bitを値として比較し、制動モード、1CB保持候補、運転者ブレーキ、車速との関係を検証した。検証は直前値を使い、車両状態100ms以内、1CB30ms以内の比較に限定。物理圧力や独立した受理確認を観測したものではない。

## 複合状態値は保持専用ではない

下位5bitが10になることを保持状態の仮説として59で調べ、5aと5cにも同じ規則を当てた。

|ルート|保持と一致|保持外を保持と誤判定|保持を見逃し|適合率|
|---|---:|---:|---:|---:|
|59|3492|5244|69|39.97%|
|5a|2694|6789|110|28.41%|
|5c|6580|8851|54|42.64%|

保持中に10が多いことだけで保持成立を判定できない。保持以外の停止や低速区間でも同じ値が出る。複合状態値の直接的な保持コードという仮説を採用しなかった。

## 運転者ブレーキとの対応

この下位5bit内のbit4・bit2は運転者ブレーキと強く対応する。bit4を例にすると、適合率・再現率は59で99.22%・99.22%、5aで99.30%・99.30%、5cで99.69%・99.75%だった。bit2も同程度。

比較対象は記録されたcarState.brakePressed。参照したローカルNissan Leaf実装では0x239のUSER_BRAKE_PRESSEDから生成され、2AAをそのままcarStateへ読み戻す循環した比較ではない。ただし記録時ソフトとの完全な版一致確認、bitの送信元、ECU仕様上の名称は未確認。5cでは両bitの例外も少数あり、同義の重複bitと断定しない。

残るbit0は速度と関係し、3ルートともON時は車速が約10km/h以上だった。しかし動いていてもOFFの区間があり、単純な停止／移動フラグではない。切り替え付近の速度のばらつきもあるため、正確な速度閾値・ヒステリシスは確定していない。

以上から、2AA下位状態はペダル状態・速度関連の情報が混在しているという見方が有力。制動要求の反映に加えて車両状態を載せていても、ブレーキECUの受理応答であることの証明にはならない。

## 観測用DBC

2AAにAUX_STATE_RAW5を追加。先頭word下位5bitをそのまま表示し、物理的な名称は与えていない。3ルート175,853フレームで独立したbyte式と照合し、不一致0。既存のopenpilot車両制御用DBCは変更していない。

## ここまでで整理できたこと

受信ログから、通常制動の数値、数値の反映、保持中に残るモードbit、保持状態の候補、RES・ペダルによる解除の違いを識別する材料は得られた。2AAの数値・有効フラグ・複合状態値のどれについても、独立した受理保証として扱える根拠は得られていない。

残る大きな問いは、1C3 bit2が指令か状態の反映か、保持成立に別の要求が必要か、純正ACCを置き換えた後も保持・解除経路を利用できるか。現状の受信ログでは候補信号が純正動作中に協調して変化するため、受信時刻の前後関係だけでは因果を分離しきれない。

同じ条件の走行ログを増やすより、対象年式・ECU構成に合う整備資料の通信系統図・送受信一覧を確認することを次の優先事項とする。既存ログでの追加解析余地はあるが、直接制御の可否を決める確度は、送受信主体の裏付けなしでは上げにくい。年式とバッテリー仕様が資料選定に必要。
