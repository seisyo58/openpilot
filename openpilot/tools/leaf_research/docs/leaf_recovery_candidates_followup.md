# 再開手段の候補整理：限定的な検証へ

2026-11-04。新しい車両要求・試験予約・commaの変更は行っていない。通常leaf-customへの復帰済みという前回確認状態を前提にしたPC上の調査。

## 見立ての修正

再開専用のCommunicationControl要求が肯定されることだけを唯一の復帰経路にする必要はない。通常診断セッションへの移行は自車75Dで既に肯定応答を確認しており、一般仕様ではその移行に伴い通常通信が再有効化される規定がある。ただし、実際の通信停止から戻った実測ではない。

停止→再開の順序自体は未実施。「事前の再開要求拒否」だけでは、その順序で失敗することまでは証明しない。一方、7F 28 11は標準上サービス非対応であり、すでに通信が有効だから拒否されたと説明する根拠もない。

## 優先順位

|候補|根拠|現在の証拠|次に確かめること|
|---|---|---|---|
|通常セッションへの復帰|AUTOSAR SWS_Dcm_00860に通信再有効化の規定|10 01の肯定応答は実測済み|セッション状態が3→1になったこと、将来は停止通信も戻るか|
|S3自動タイムアウト|非通常セッションで診断要求がない場合の通常復帰という仕組み|自車の時間・実装は未確認|診断送信を止めた期間の後に通常へ戻るか|
|車両OFF、スリープ、再起動|一時診断状態が解除される可能性|停止後の解除・対象ECU電源断は未確認|OFF後の状態、ON時に他の処理で上書きされる前の状態|
|明示的な通信有効化|UDS 28 00 01の候補|拡張03では7F 28 11|同じ要求の再試行は優先しない。別形式には根拠が必要|

## 診断状態を測る読み出し候補

ローカルopendbcとudsoncanでは、DID F186はActive Diagnostic Session。自車75Dで対応しているかは未知。F187/F188/F191に同じ品番文字列が返ったこともあるため、F186への応答を無条件で状態番号と見なさない。

限定試験を設計するなら、まず通常状態で22 F1 86を一度読み、正しい62 F1 86と期待する状態データを確認する。未対応・無応答・品番文字列等の想定外形式ならそこで中止する。

読める場合は、既確認の10 03と10 01に対応して3・1の状態が観測できるか確認する。その観測方法が成立してから、送信なし待機による自動復帰やOFF/ON後の状態を比較する。

S3の測定中に繰り返し読み出すと、その読み出し自体が診断タイマーを更新し得る。無送信の待機区間を設け、最後に一度だけ測り、他の診断クライアントの送信もログで除外する必要がある。P2*=5000msはS3の実測値ではない。

OFF/ONの試験では、起動処理が先に通常セッションへ戻してしまうと「OFFで戻った」という検証にならない。最初の測定前の診断送信も監査する。車両OFFが対象ECUの完全な電源断になるかは別の問題。

これらでセッション復帰を測れても、通信停止後の再開が保証されるわけではない。停止→通常復帰の確認は、その後の独立した限定試験となる。

## 総当たりの扱い

対象75Dと既確認の1・3セッション、根拠のある読み出しを固定して一括比較することはできる。未知アドレス・全サービス・全セッションの走査にはリセット、プログラミング、書換え、作動試験等が混ざり、意図しない状態変更が起きる。今回はその走査や、新しいリセット・バッテリー切断操作は行わない。

## 資料

- [AUTOSAR DCM R21-11、SWS_Dcm_00860](https://www.autosar.org/fileadmin/standards/R21-11/CP/AUTOSAR_SWS_DiagnosticCommunicationManager.pdf)：通常セッション移行時の通信再有効化。自車のAUTOSAR採用・規格遵守を証明するものではない。
- [udsoncanのDID定義](https://udsoncan.readthedocs.io/en/latest/_modules/udsoncan/common/dids.html)：F186の識別名。
- [AUTOSAR Diagnostics R22-11](https://www.autosar.org/fileadmin/standards/R22-11/AP/AUTOSAR_SWS_Diagnostics.pdf)：診断要求の受信とS3タイマーの関係の例。Adaptive側の一般仕様であり、自車実装を特定する資料ではない。

通常復帰の仕組みは仮説として有力だが、自車の停止通信が戻ったという実測はまだない。復帰候補の特定と、停止後の機能回復の証明を区別する。
