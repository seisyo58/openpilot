# 要求反映と受理確認の切り分け・観測DBC更新

今回の作業は、2AAの数値・状態bitを3ルートで追い、受理確認として使える信号を探すことと、これまでの観測をDBCへ反映すること。

## 2AAで追加確認できたこと

bus0 2AA byte2 bit5は、3ルート計175,853フレームすべてで、同じフレーム内の先頭数値が正であることと完全一致した。これを独立した受理確認bitとして扱う根拠はない。

1C3の数値・bit7との対応も約25ms遅れが最良で、正の数値に関係する比較点におけるbitのF1は59で0.9983、5aで0.9986、5cで0.9994。これは信号の関連であり、受理率ではない。フレーム周期の異なる信号を直前値で照合している。

1C3 bit2や1CB保持候補bitについては、2AAの非数値領域および先頭wordの下位5bitに、3ルート共通で直接対応する単独bitは見つからなかった。探索対象は単独bitの正論理と一定遅延の対応であり、多bitの状態値・負論理・独自プロトコルまで否定するものではない。

従って2AAは『要求が別メッセージに反映される経路の候補』としては強くなったが、『ブレーキECUが受理した証明』としては使えない。転送・再符号化・受信側応答の区別は未決着。

5cでは1CB・2AAはbus0とbus1の両方、1C3・2B0・28E・28F・2D4は調査した保持前後の窓でbus1のみ観測された。bus0/bus1に同じpayload・同じlogMonoTimeの記録が多く、ログ上の受信時刻から物理的な送信元や厳密なゲートウェイ通過時間を決めることはできない。

## DBCに反映した内容

更新ファイルは `leaf_longitudinal_candidates.dbc`。車両本体や使用中のopenpilot DBCは変更していない。

- 2B0の最新の上位ニブル修正候補を追加。以前の候補は比較用として残し、コメントで区別。
- 1C3 bit2が数値ゼロでも保持中に残ることと、bit7が正の数値と一致することを記載。
- 1CBの保持候補2bitを追加。同義とは断定せず独立フィールドにした。
- 2AAの先頭raw11数値と正の値フラグを追加。raw10との比較には2倍する。
- 2D4・28Fの走行要求有効に関連する候補bitを追加。
- 0x30FとHUDが5cで一致しない例をコメントに追記。
- 実受信DLCに合わせ、2D4は6byte、28Fは5byteで定義。

openpilotのDBCパーサーで読み込み、3ルートの対象1,580,664フレーム、計2,459,244フィールド値を独立したbyte式と照合し、不一致0。5c元ログのDLCとも6メッセージすべて一致した。検証は受信フィールドの位置・幅・生値であり、物理校正や送信受理ではない。

## 現在の観測モデル

|観測対象|候補|今言えること|
|---|---|---|
|自動制動の数値|1C3数値・bit7|bit7は正の数値に一致|
|要求の反映|2AA先頭数値・byte2 bit5|約25ms遅れて1C3数値に対応。独立ACKとは確認できない|
|制動モードの継続|1C3 byte5 bit2|数値ゼロでも保持中はON。指令／応答の区別は未確定|
|保持成立の状態|1CB byte4 bit0等|全7例の安定保持でON、RES・ペダル介入でOFF|
|走行要求の有効性|2B0・2D4・28Fの候補bit|3ルートでほぼ同じ状態を示す|

## 次に残る判別

受信ログからは、保持の入口・維持・解除を見分ける観測器を構成できるだけの候補が揃った。一方、1C3 bit2をこちらから維持すれば保持できるか、2AAがどのECUから出ているか、純正ACCを外すと保持の条件が残るかは受信だけでは確定できていない。

次の受動解析として残るのは、2AAの複数bit状態値と、数値ゼロ時の1C3・1CB・2AAの状態組み合わせを追うこと。実車用の送信実装へ移すには、これとは別にECU間の接続・送信元・受理条件の裏付けが必要になる。

詳細データは leaf_2aa_internal_consistency.json、leaf_2aa_all_status_associations.json、leaf_observer_dbc_checks.json。関連する過去の停止中ACC有効化の結果は leaf_stationary_engage_findings.md。
