# 停止保持・再発進の設計に関する追加確認

2ルートの全受信CANから再開待ち候補bitの6区間を抽出。終了まで見える5区間のうち4区間でRES、1区間でアクセル操作を確認した。残る1区間はrlog欠損で終了が見えない。

|ルート|再開待ち開始 秒|観測した待ち時間 秒|終了前の操作|操作から表示状態解除まで|
|---|---:|---:|---|---:|
|59|438.507|26.179|アクセル|約78ms|
|59|528.426|1.870|RES|約90ms|
|59|679.046|17.180|RES|約80ms|
|5a|116.982|3.559|RES|約80ms|
|5a|282.952|18.120以上|欠損のため不明|不明|
|5a|399.572|5.710|RES|約69ms|

待ち時間は最後の候補bit ONフレームまで。解除時刻は次のOFFフレームなので、待ち時間と操作から解除までの基準には約100ms周期分の違いがある。RESは受信bus0 0x239のボタンbitであり、その発生源をこのbitだけから運転者／装置に識別していない。

RESの4例はいずれもアクセル・ブレーキ介入とACC解除が周辺窓内に見られず、2B0が再び有効になり、表示状態解除から約0.84～1.18秒後に車速が1km/hを超えた。2B0再有効化は表示状態解除より約9～10ms前。1C3の正の要求はその前後1秒・後3秒の調査窓内にない。これは純正が再開待ちからRESで走行へ戻れることを示す。

再開待ちの内部（開始0.2秒後～最後のONフレーム）では2B0の有効要求は全6区間で0フレーム。1C3は待ち開始後0.22～0.70秒までは正の要求が残ったが、その後はゼロだった。表示状態の移行と実際の要求消失は完全に同時ではない。長い区間では要求がゼロになった後も車速ゼロが続く。

ただし両ログともe-Pedal ON。車速ゼロの継続から、ACC専用のラッチ保持、e-Pedalの保持、その他の保持を識別できない。1C3ゼロのまま停止することだけで、ブレーキ力がゼロ、あるいは特定ECUが保持していると断定できない。

## 設計への意味

純正ACCの再開待ちを利用し、必要時にRESで再開させる構成は、今回の観測で動作経路が確認できた。3秒遷移を避けることを必須目標にする必要はない。

一方、純正ACCを外して2B0・1C3を直接制御する構成で、保持を継続できるか、RESが同じ意味を持つかは未検証。今回のRES成功例には純正ACCが残っている。特別パターンを3秒超維持した場合の受理・保持・解除の挙動も、既存ログには観測例がない。

従って直接制御については、(1)自前の保持要求を継続する案、(2)車両側の保持へ移して解除する案、の両方が残る。既存ログから後者が独立に利用可能とまでは確定できない。安全な解除・制御喪失時の保持挙動はどちらの案にも必要。

追加ログで判別力が高いのはe-Pedal OFFでの純正ACC停止保持・RES再発進、保持中のブレーキ操作とACC解除の記録。既存条件のままログを増やすより、e-Pedal保持との交絡を減らせる。純正ACCを外した際の受理条件は、受信ログの追加だけでは確定できず、制御ECUの仕様確認または隔離された検証が必要になる。

数値詳細は leaf_hold_release_evidence.json。抽出処理は work/hold_release.py に保存。車両への送信・実機設定変更は行っていない。
