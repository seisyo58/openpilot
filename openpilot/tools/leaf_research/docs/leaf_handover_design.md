# Leaf縦制御：取得・解除の試験モデル

2026-11-03。ブランチexperiment/leaf-longitudinal、コミット7f4a9028a9。

## 今回の実装

記録ツールに続き、取得・解除の状態管理をファイル入力だけで検証するhandover.pyを追加した。

待機 → 取得確認待ち → 模擬有効 → 解除確認待ち → 待機。

- 開始には入力が新鮮・中立で、開始操作が新しく立ち上がることが必要。
- ブレーキ・アクセル介入、入力途絶、停車、ギヤ変更、開始操作の解除は解除待ちへ移る。
- 解除確認がなければロックする。入力が戻っても解除済みと扱わない。
- 動作中の時刻異常や記録ギャップは解除状態不明としてロックする。
- 過去の試行の応答や種類の違う応答では状態を進めない。
- 取得／解除確認は模擬応答専用。車両CANを実際の取得／解除確認として扱う処理はない。
- 全状態で送信許可はfalse。実車用の送信処理・パケット・Panda変更は含めない。

取得・解除待ち0.5秒などの閾値は試験用の仮値であり、車両で確認したタイムアウトではない。

## 検証

合計16テストが成功し、Ruffとgit diff --checkも成功。今回のREADY・Pレンジの1082サンプルを再生すると、開始操作を注入していないため全件待機のまま。これは保存データとの結合確認であり、車両での取得・解除成功の証拠ではない。

## 実送信までに必要な確認

現行ソース：opendbc_repo/opendbc/safety/modes/nissan.h

1. Nissanの通常LeafおよびPPP用TX許可リストには、0x2B0と0x1C3がない。送信には専用の要求値・変化率・介入・鮮度などの安全検査が必要。許可リストだけ追加する変更は今回行っていない。
2. 両候補はbus 1で観測されている。現行のNissan転送処理は一部のbus 0/2メッセージを扱っており、これらの縦方向要求を置き換える仕組みは実装されていない。
3. 同じbus 1上の純正送信を、現在のハーネスで分離・差し替えできるかは未確認。元の送信を残したまま同じIDを送る方式で正常に引き継げるとは仮定しない。
4. 実車が受理・解除した証拠として使える応答、通信断時の挙動、要求値と実際の駆動・制動量との対応は未確定。

次に優先するのは、ハーネス配線・ECU間の接続経路とbus 1の役割の確認。そこから直接上書き可能な経路があるか、別の試験用接続が必要かを判断する。今回の記録確認だけを根拠に実車へ送信する段階には進めていない。
