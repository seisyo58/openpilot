# 縦制御の3経路：接続関係と次に必要な証拠

2026-11-05。基点 `8b12f550c2`。既存の受信抽出NPZ、抽出スクリプト、現行Panda/safetyコード、保存済み配線図を照合した。車両への接続・送信・設定変更・試験予約は行っていない。

## 今回進んだ点

**1D6はbus0だけの信号ではない。3走行でbus0とbus1に継続し、bus2の記録は開始から約7～9秒までに限られた。** 同じ傾向が180・1CBにもある。一方30Fはbus2に継続し、bus0の記録が起動直後に限られる。

これは、0/2の接続が分離された後に、1D6が車両側、30FがADAS側で受信される構成と整合する。**既存ハーネスで1D6を差し替えれば車両側の制動受信先へ届く、という見込みを支持する結果ではない。** リレー状態や実機FWを原rlogから再確認していないため、分離時刻・物理送信ECU・受信ECUの確定とはしない。

これまでの[1D6調査](leaf_total_deceleration_request.md)の「Bus 0の候補」という表記は受信解析の着目点であって、bus0専在やハーネスを跨ぐ要求経路を意味しない。

## 1. 受信記録の再集計

[監査JSON](../evidence/leaf_transport_visibility_20261105.json)は以下3ファイルを実際に再読込した結果。ファイル全体のSHA256も保存した。

|走行末尾 / 抽出ファイル|1D6 bus0|1D6 bus1|1D6 bus2|bus2の最終1D6（開始から）|30Fのbus0最終 / bus2最終|
|---|---:|---:|---:|---:|---:|
|59 / acc_frames.npz|87,054|86,894|918|9.198秒|9.179 / 870.556秒|
|5a / route5a_frames.npz|63,485|63,329|846|8.473秒|8.425 / 874.852秒|
|5c / route5c_frames.npz|200,995|200,831|708|7.105秒|7.094 / 2010.369秒|

5aは途中欠損を含む。記録範囲を連続走行時間や欠落のない受信として扱わない。

各走行の「bus2の最終1D6 + 1秒」以降を単なる観測窓として集計した。bus0にはそれぞれ86,041 / 62,544 / 200,192フレーム、bus1には86,030 / 62,539 / 200,185フレーム残る。bus2の30Fも8,620 / 6,263 / 20,058フレーム残る。bus2全体の記録が終了したため1D6が見えなくなった、という説明ではない。

同窓の1D6先頭16bit値の範囲はbus0・bus1とも、59が6961～12000、5aが7006～12000、5cが12000固定。e-Pedal ONとされた59/5aでは、起動直後だけでなくこの後続窓にも変動がある。これも要求の受理や物理単位の証明ではない。

59/5aでは169がbus2で継続し、bus0ではそれぞれ9.217 / 8.473秒で記録終了する。30Fと同方向の補助証拠。5cの抽出対象には169が含まれないため、5cの169不在という結論は出さない。

### 記録形式による限界

- 抽出元 `extract_acc.py` / `extract_route5a.py` / `extract_route5c.py` は `can` 内の `src < 3` を採用する。配列は `[Event時刻, byte0, ..., byte7]`。DLC列のある別形式のNPZは今回扱わない。
- `panda.cc` のCAN展開ではreturnedに+128、rejectedに+192を付ける。現在コードのその仕様では、単なる転送送信記録はこれらのRX配列に含まれない。ただし走行時のFW一致は未監査。
- CANの複数フレームは同一Event時刻になる。bus0とbus1で同時刻に見えることを、伝播遅延ゼロ・同一物理バス・ECU内転送の証明としない。
- 今回利用した旧キャッシュ索引の59原rlog参照先は現存しなかった。原rlogから抽出全体を再実行した結果ではない。NPZにないキーは「未採録」とし、0フレームと区別した。

## 2. 配線とコードから描ける接続図

公式hardwareの固定版 `3e04f5c2a7c4309e90e60ff65f0e92b47a7d256f` を使用。
[BUILD_HARNESS](https://github.com/commaai/hardware/blob/3e04f5c2a7c4309e90e60ff65f0e92b47a7d256f/harness/BUILD_HARNESS.md)はghで再取得し、保存済み版の接続説明と照合した。[Nissan A v3配線図](https://github.com/commaai/hardware/blob/3e04f5c2a7c4309e90e60ff65f0e92b47a7d256f/harness/v3/Nissan_A_Harness.pdf)は既存のページ画像を目視確認した。図の端点名はTO ADAS UNIT / TO CAR。実車のハーネス版・向き・装着ユニット名を今回確認したものではない。

```text
ADAS側端点 ─ CAN2 ─ [閉リレーで直結 / 開リレーでPanda中継] ─ CAN0 ─ 車両側ネットワーク
                   30F側の観測                         1D6側の観測

別のCAN対 ───────────── 純正配線を通過 ──────────────────
                              └ CAN1へ分岐（遮断箇所なし）
                                1C3 / 2B0、1D6も記録
```

0/2の向きは通常の論理配置を示す概念図。ハーネス反転とソフト側のbus lookupを区別する。図はVCM・EDIBが同じ側にあると確定した実車配線図ではない。

現行コードの根拠（すべて基点コミットで確認）:

- `opendbc_repo/opendbc/safety/safety.h` の `get_fwd_bus`: 0→2 / 2→0 / 1→転送先なし。
- `opendbc_repo/opendbc/safety/modes/nissan.h` の `nissan_fwd_hook`: 1D6の個別遮断はない。1D6はLeafのホスト送信許可一覧にもない。
- `panda/board/drivers/fdcan.h`: RXフレームを転送判定し、別途送信側のreturned記録を作る。元の受信側に既に届いたフレームを取り消す処理ではない。
- `panda/board/drivers/can_common.h` の `can_flip_buses`: 0/2のlookup交換で、bus1に分離経路を作る処理ではない。

したがって、仮に1D6の制動受信ECUが送信元と同じ車両側にあるなら、0→2転送を止めてもそのECUへの純正要求を遮断できない。受信先がADAS側にあり別経路で制動を要求する可能性等は、この集計だけでは排除できない。

## 3. 3経路の判断と未確認点

|経路|現在の証拠|進めるために必要な証拠|今回の判断|
|---|---|---|---|
|1C3/2B0を直接置換|既存記録ではbus1。現行CAN1は分岐|物理送信元・受信先、正規の停止/復帰か、分離できる接続箇所|同じ線への追加送信やsafety許可追加へ進まない|
|75Dで純正送信停止|識別・拡張セッションは応答。事前通信有効化は拒否。停止自体は未送信|同型ECUの成功した停止/復帰手順、停止範囲、関連機能への影響|新しい根拠のない診断引数探索は保留|
|1D6経路を利用|今回bus0/1継続・bus2起動直後のみを3走行で再確認|1D6の実送信元・受信先と、両者を分けられる接続箇所|既存0/2中継で制動要求を置換できる見込みは下がった。追加ハード不要の代替と扱わない|

1C3/2B0と75Dの対応も、1D6のVCM→EDIBという解釈も未確定。診断応答バスや品番群だけから物理送信元を埋めない。

### 置換対象と一緒に追うべき依存候補

|対象|既存の観測|未確定の区別|
|---|---|---|
|2D4 / 28F候補bit|2B0有効状態とほぼ一致|要求を受けるための許可か、状態表示か。同じECUの送信か|
|1C3 bit2 / bit7|数値0の状態継続と正の数値を区別|ホストが維持する要求か、車両内部状態の反映か|
|1CB / 2AA|制動・保持との対応、要求候補との時間関係|受理ACKか、共有する内部量か。実回生・実油圧とは未校正|
|30F / 4CC|保持・RES待ち・表示との対応|表示と動作許可の境界、停止対象ECUとの関係|

これらは「一緒に送るべきID一覧」ではない。関連する観測と受信側依存関係を切り分けるための調査項目。

## 4. 次の作業の入口

今回の到達点は、1D6を既存ハーネスだけで使う近道の根拠が弱くなったこと。通常走行ログや同じ診断小試験の追加では、物理送信元・受信先の空欄は埋まらない。

次は日本2022仕様に対応する構成図・CAN信号送受信表が得られた際に、上表の送信元/受信先と分離箇所だけを照合する。同型ECUの正規診断記録が得られた場合は、停止・復帰範囲を別途評価する。既に調べた公開コードや別年式資料の再検索だけを進展と数えない。購入・販売店への連絡・機器選定は行っていない。

資料が得られるまでローカルで進められる別作業は、通常駆動→協調制動→保持→解除の受信イベント分類。これは将来の要求モデル評価には使えるが、制御権の引き継ぎ問題を解決しない。

## 再現

```sh
.venv/bin/python openpilot/tools/leaf_research/audit_transport.py \
  /path/to/work/acc_frames.npz \
  /path/to/work/route5a_frames.npz \
  /path/to/work/route5c_frames.npz \
  --out /tmp/leaf-transport-visibility.json
```
