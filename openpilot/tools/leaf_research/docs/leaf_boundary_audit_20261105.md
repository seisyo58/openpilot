# 特別パターンの境界：e-Pedal OFFとの比較と時刻の不確かさ

2026-11-05。3走行の既存受信NPZを再集計。従来の[入口・出口の詳細調査](leaf_switch_deep_findings.md)を5cへ広げ、単一の近接エッジを恣意的に選ばない方法と、変化前後の受信時刻を使った比較を加えた。実車への接続・送信・制御変更はない。

## 結論

- e-Pedal OFFとされた5cでも、走行中の特別パターン入口39境界で近傍の1C3立ち上がりを観測した。単独で対応した32例の最初の正数受信は、特別パターンの最初の受信より約7～20ms早い。残り7例は近傍に複数の立ち上がりがあり、単一対応としない。
- ただし、この32例のうち30例では両信号の変化前後の受信区間が接するか重なり、2例は同一Event時刻内の変化を含む。受信時刻の差を、そのまま送信側の必須順序や10ms待機へ移せない。
- 出口では1C3が0になった後に特別パターンが残る傾向があるが、5cの単独対応30例で約10～161msと幅がある。共通の固定待ち時間は得られない。
- 入口直前の通常要求候補qもON/OFFの走行で異なる範囲に分布する。物理単位や設定単独の因果は未確定で、共通の送信用しきい値を採用する根拠にはならない。

## 1. 選別と対応付け

[audit_boundaries.py](../audit_boundaries.py)と[監査JSON](../evidence/leaf_boundary_audit_20261105.json)を追加した。

1. 2B0の特別パターン `a8 27 d5 ac 5b 00 ?e 09` が100ms以上観測された区間を取得。30ms超の欠損で分割する。
2. 入口は非特別→特別、出口は特別→非特別の隣接受信。欠損・ファイル端で境界が見えない場合は打ち切りとして残す。
3. 下表の主集計は、境界時点の車速3km/h超、前後200msの車両状態でACC有効・ペダル非操作を確認でき、通常側の2B0有効bitもONの境界に限定する。carStateは直前100ms以内のみを採用し、状態の欠損も除外する。
4. 入口では1C3の0→正、出口では正→0の全エッジを、基準の前後200msで列挙。候補が複数なら複数のまま保存し、時間差の要約には単独対応だけを使う。
5. 受信/送信要求のRES・SET・CANCELを前0.5秒～後0.7秒に注記する。ボタンの見えない部分集合も別集計するが、純正だけの動作と認定しない。

前後の状態を使う後ろ向きの選別であり、未来の切り替えを予測する性能評価ではない。

## 2. 入口の比較

時間差は `1C3最初の正数受信 − 2B0最初の特別パターン受信`。負なら記録上1C3が先。

|走行|e-Pedal申告|入口境界|単独対応 / 複数対応|単独対応の時間差 最小 / 中央 / 最大 ms|
|---|---|---:|---:|---:|
|59|ON|4|4 / 0|-10.993 / -9.931 / -9.108|
|5a|ON|2|1 / 1|-10.292 / -10.292 / -10.292|
|5c|OFF|39|32 / 7|-19.812 / -10.291 / -7.288|

この選別内に近傍エッジが0件の入口はない。複数対応は「対応しない」ことも「特定の一つが原因」も意味せず、1C3の短い再立ち上がりを区別できていない例として保持した。5aの274.471秒入口はその一つで、従来の単一値対応から扱いを厳しくした。

### 最初に変わった受信時刻だけを比べない

各エッジについて「最後に旧状態を受信した時刻～最初に新状態を受信した時刻」を保存した。典型例は、2B0特別化を0msとして以下の形。

```text
1C3: 最後の0値      約-20ms ───── 最初の正数 約-10ms
2B0: 最後の通常値                   約-10ms ───── 最初の特別 0ms
```

最初の新状態だけなら約10ms差があるが、観測区間は接する。さらにCAN Eventは複数フレームをまとめて記録するため、これらを厳密なハードウェア時刻の上下限と見なすこともできない。

|走行|観測区間が接する/重なる|どちらかが同一Event時刻内で変化|厳密に離れた観測区間|
|---|---:|---:|---:|
|59の単独対応4例|3|1|0|
|5aの単独対応1例|1|0|0|
|5cの単独対応32例|30|2|0|

5cの408.472秒入口では1C3の0→正の前後が同じEvent時刻に入り、最初の正数は約19.8ms先行して見える。765.795秒入口では2B0通常→特別の前後が同じEvent時刻に入る。これらを「1周期より長い待ち時間が必要」という根拠にはしない。

## 3. 出口の比較

時間差は `1C3最初の0値受信 − 2B0最初の通常側受信`。

|走行|出口境界|単独対応 / 複数対応|単独対応の時間差 最小 / 中央 / 最大 ms|
|---|---:|---:|---:|
|59|4|4 / 0|-78.969 / -40.460 / -30.533|
|5a|2|2 / 0|-20.494 / -15.541 / -10.588|
|5c|32|30 / 2|-160.707 / -40.719 / -10.201|

5cの単独対応30例のうち、25例は1C3の変化観測区間が2B0より前に離れている。3例は接する/重なる、2例は同一Event時刻内の変化を含む。入口に比べ、出口では単なる最初の受信時刻差以外にも状態の残留を観測できる例が多い。

それでもECU内部の順序・要求受理・必要待機時間を確定したものではない。近傍エッジ対応には別の制動パルスが混ざる可能性があり、窓内の単独対応であることが因果を保証するわけではない。

## 4. 通常要求候補qの境界値

最新の通常値候補式を使い、入口は最後の非特別・有効フレーム、出口は最初の非特別・有効フレームを読む。特別パターンを通常値の式へ混ぜない。

|走行|入口直前qの範囲|出口直後qの範囲|近傍ボタンのない入口数 / 全入口|
|---|---:|---:|---:|
|59|11059～11367|11353～11359|3 / 4|
|5a|11240～11348|11353～11359|1 / 2|
|5c|10071～10699|9940～10782|35 / 39|

ボタンのない部分集合でも5cの入口範囲は10071～10699のまま。59では11059～11350、5aでは残る1例が11348。単に近傍のボタン付き入口を外しても、3走行の入口が一つのqへそろうわけではない。

ただし速度・SOC・勾配・D/B・ECO・先行車条件等を揃えた実験ではない。e-Pedal設定だけが境界値を変えたとは言わず、設定ごとの換算や送信しきい値も作らない。今回の入口直前値はサンプル値であり、ECU内部で判定した瞬間の要求値でもない。

## 次へ残す判断

受信観測器では入口、制動中、1C3数値ゼロ後の残留、通常復帰を分けて記録できる。送信モデルでは「先に特別パターンを送って固定時間待つ」「1C3が0なら即通常へ戻す」のどちらも、この受信比較だけでは裏付けられない。

調査は、2ルートの少数入口から、OFF側を含む45入口・38出口の選別済み境界へ進んだ。追加の通常ログを無条件に集めるより、次はSOC・D/B・ECO等の設定/条件情報を原rlogで確認できるか、または送受信ECUの資料が得られるかが判断の入口になる。今回Connectからの再取得は行っていない。

## 再現

```sh
.venv/bin/python -m openpilot.tools.leaf_research.audit_boundaries \
  /path/to/work/acc_frames.npz \
  /path/to/work/route5a_frames.npz \
  /path/to/work/route5c_frames.npz \
  --tx-59 /path/to/work/route59_tx.npz \
  --out /tmp/leaf-boundary-audit.json
```

ファイル名・SHA256・全候補・除外した文脈をJSONに保存し、出力の上書きを拒否する。原rlogの再抽出ではなく、[元の抽出形式と限界](leaf_transport_paths_20261105.md)を引き継ぐ。
