# リーフ縦方向制御：調査履歴を踏まえた見解と次のアプローチ

日付: 2026-11-05。ユーザーの「見落としや考えられるアプローチはあるか」という依頼に対するCodexのレビューを保存する。

対象: `research/leaf-longitudinal-observations`、レビュー時のHEAD `15f5f77fd3ff1c65518f223d9ff423cccb758da4`。日本仕様ZE1 e+ G、2022年6月、通常Nissan Aハーネスという既存調査の条件を引き継ぐ。

## レビューの範囲

HANDOFF、個別調査報告、保存された監査JSON、現行のNissan制御コードを確認した。公開情報は主にgh経由でStarPilotのNissan実装・変更履歴とcommaのハーネス資料を再確認した。原走行ログの全解析は再実行していない。

これは既存の観測を踏まえた解釈・優先順位の提案であり、新たな実車検証結果や独立した第三者実験ではない。過去の会話で言及された未採録レビューの復元でもない。車両への接続、CAN送信、試験予約、制御コード・Panda・実機設定の変更は行っていない。

## 主な見解

手詰まり感は妥当。調査の主要な壁は、信号の解読から、純正と競合せず制御権を取得する方法へ移っている。追加の解析には価値があるが、同じ受信条件でログや診断の小試験を増やすだけでは、この壁は解消しにくい。

ソフトウェアだけで突破できる新しい経路は、今回のレビューでは見つからなかった。ただし、全てのソフトウェア経路が不可能だと証明されたわけでもない。

### 1. 診断セッション探索の優先度を下げる

**既存の観測:** 75Dへの拡張セッション要求は肯定応答。一方、事前の通信有効化要求は拒否され、予定していた停止要求は送っていない。F186による状態取得も成功していない。[75D通信制御試験](leaf_uds_communication_attempt_001.md)

**見解:** セッション状態が分かっても、通常通信を停止する方法が分かるとは限らない。次に必要なのは、同じECUの対応手順、停止・復帰の成功記録、または正規診断操作の通信記録という新しい根拠。同じ条件での観測延長や根拠のない引数変更の優先度は低い。

別のメーカー固有手順の存在は否定できないが、その可能性だけを理由に実車の探索を続ける方針は推さない。

StarPilotのNissan interfaceの最新変更は確認時点でも `cfd221b89cec223397f0a805791136aa9b958758`。`LEAF_2025_SV_PLUS_ALPHA_LONG_ENABLED=False` で、特定の2025 SV Plusの車種・FW条件に限定されていた。このコードを、当該2022年車にも適用できる完成済みの移植元とみなす根拠は得られていない。[確認した実装](https://github.com/StarPilotHQ/StarPilot/blob/cfd221b89cec223397f0a805791136aa9b958758/opendbc_repo/opendbc/car/nissan/interface.py)

### 2. 純正の2フレームを止めるだけで成立するかも未解決

**既存の観測:** 2D4・28Fの候補bitは2B0の有効状態とほぼ一致する。ただし表示・内部状態の反映・受信側の許可条件のどれかは未確定。[状態ビットの調査](leaf_hold_mode_assessment.md)

**仮説:** ECUの通常送信をまとめて止めると、置換したい要求に加えて、受信側が要求を受理するために必要な状態通知まで失う可能性がある。両IDの送信元が同じECUであることや、これらが実際に受理条件であることは確認していない。

**提案:** 1C3/2B0の送信元だけでなく、そのECUが送る関連メッセージと依存関係を調べる。停止に成功したとしても「自前で1C3/2B0だけ送れば成立」とは仮定しない。未解読の関連メッセージを推測で生成する提案ではない。

AEB・操舵・状態通知の共存、アプリ停止・通信断時の解除と復帰も、対象2信号の消失・再出現とは別の確認事項になる。

### 3. 要求量の意味と車両応答モデルを分ける

**既存の解析結果:** 通常2B0と0x180の駆動系候補には、別ルートでも相関の絶対値が約0.9998～0.9999という強い対応がある。車体加速度への対応より安定している。[通常要求と駆動系の対応](leaf_drive_and_regen_findings.md)

**見解:** 2B0を初めから物理加速度の指令として扱わず、次の二つを分離して考える。

- 2B0が駆動系のどの要求量・内部量を表すか。
- その量に対し、実際の車体加速度がどう変わるか。

純正ACCが閉ループで出した要求と加速度の回帰には、勾配・抵抗・純正側の補正も混ざる。また0x180が要求の変換・反映なら、非常に高い相関でも独立した実応答の証明にはならない。現在のデータから0x180が単なる反映だと確定したわけではない。

送信用の換算式を決める前に、符号化・要求量の意味・車両応答を分けるべきという提案。既存回帰のゼロ点や係数を実車送信へ採用する根拠を追加したものではない。

### 4. 回生・摩擦の配分をホスト側で再現することを必須にしない

**既存の観測:** 1C3を摩擦専用、2B0の特別パターンを一定の強い減速度とみなす根拠は不足している。通常時は2B0の連続値が駆動系候補に対応し、制動時は2B0が固定パターンのまま別の協調信号が変化する。[協調制動の解析](leaf_braking_coordination_findings.md)

**優先して検証したい仮説:** 通常の駆動要求から、車両側の協調制動へ要求経路を切り替えている。この場合、配分アルゴリズムの完全再現より、各モードの要求・有効条件・解除条件の理解が重要になる。

通常駆動・協調制動・保持・解除の候補モデルを整理し、それぞれの仮説を区別できる観測を決める。単一の減速度閾値や固定待ち時間で状態遷移を作る根拠はまだない。

1D6のe-Pedal経路も代替候補として残る。ただし、bus0に見えるだけでは置換可能とはいえない。送信元と受信先がハーネスの同じ側なら、その中継箇所では要求を差し替えられない。1D6の方向・受信先・受理条件は未確定。[配分前要求の調査](leaf_total_deceleration_request.md)

### 5. 可逆的な中継経路は、診断停止への依存を変えられる

**既存の根拠:** 通常Nissan Aの対象候補はbus1に記録されている。ハーネスのCAN1は読み書き用の分岐で、純正フレームを遮断する経路ではない。[配線・転送の調査](leaf_longitudinal_transport_findings.md)、[comma公式ハーネス資料](https://github.com/commaai/hardware/blob/3e04f5c2a7c4309e90e60ff65f0e92b47a7d256f/harness/BUILD_HARNESS.md)

**提案:** 追加ハードウェアを許容するなら、物理送信元を特定したうえで、その接続に可逆的な中継経路を作れるか検討する。成立すれば、未知の診断停止機能を探すことへの依存を外し、送信方向の確認や特定メッセージを扱うベンチ検証へ進める。

追加CAN機器を同じ線につなぐだけでは純正との競合は解消しない。送信元と受信先を分けて中継できる構成が必要。現在の操舵側中継との両立、終端・故障時の経路も設計事項になる。具体的な購入・配線変更はまだ提案しておらず、中継だけで指令受理や停止保持が成立するという意味ではない。

## 今後の優先順位

|制約・目的|次に価値がある作業|判断の境界|
|---|---|---|
|ソフトウェアだけで進めたい|同一ECUの停止・復帰の成功根拠を探す|新しい根拠が得られるまで追加の診断小試験は保留するという提案|
|直接縦制御を実現したい|送信元・受信先・関連メッセージを特定し、可逆的な中継／ベンチ構成を検討|適合する接続経路が確認できる前に機器や配線を決めない|
|今の資料で解析を進めたい|駆動要求・協調制動・保持・解除の候補モデルと、各仮説を区別できる観測を整理|受信波形の再現を実車の指令受理と扱わない|

レビューとして推す次の目標は、**1C3/2B0の物理送信元と、置換に必要な依存関係を確定すること**。資料購入は必須の既定路線にせず、同型ECUの情報・既存ログ・適合配線資料などから何が解けるかを個別に判断する。

これは今後の選択肢の提案であり、実験・購入・配線変更を実施する承認や予約ではない。次の作業では、このレビュー時点の状態と現在の車両・リポジトリ状態を区別する。
