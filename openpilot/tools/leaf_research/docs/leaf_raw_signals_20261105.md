# 復旧原ログの信号整合性とPanda returned記録

2026-11-05。[原rlog復旧](leaf_raw_recovery_20261105.md)の3走行を再監査した。実車通信・送信・制御変更はない。

## 1. 符号化の照合を欠損解消後にも実施

|走行|1C3フレーム|加算チェックサム不一致|byte5 bit7とraw10正の不一致|2B0フレーム|反転/分数冗長符号の不一致|
|---|---:|---:|---:|---:|---:|
|59|86,888|0|0|86,888|0 / 0|
|5a|87,320|0|0|87,319|0 / 0|
|5c|200,812|0|0|200,812|0 / 0|
|合計|375,020|0|0|375,019|0 / 0|

1C3の式は `raw10=((b0&63)<<4)|(b1>>4)`、checksumは `(1+0xC3+sum(b0..b6))&255`。2B0は公開式によるraw12の反転整合と、最終byteの2bit分数/反転整合を確認した。冗長符号が一致することと、通常量の数値上の桁重み・物理単位が確定することは異なる。

1C3 raw10の範囲は59が0～829、5aが0～763、5cが0～781。物理圧力・摩擦専用要求・総制動要求の区別は今回も確定していない。

### カウンターを『全て連続』とは言わない

隣接受信間隔30ms以下で、1C3の2bit、2B0の4bitカウンターの差分を調べた。

- 59は全て+1。
- 5aは8.492秒に、両IDとも+2を1回記録した（受信間隔約19.7ms）。
- 5cは7.133秒に、両IDとも+2を1回記録した（受信間隔約9.6ms）。

いずれも起動診断から通常safetyへ移る近傍。受信欠落・記録のまとめ方・カウンター側の変化等を区別できず、送信ECUの故障や途絶と断定しない。30ms超の間隔は別途除外しており、この検査だけで原ログの無欠損を保証しない。

## 2. 1D6の通常受信とreturnedを分ける

開始30秒以降の記録を比較した。

|走行|1D6通常RX bus0|通常RX bus1|通常RX bus2|src130 returned|ホストsendcan（全区間）|
|---|---:|---:|---:|---:|---:|
|59|84,061|84,050|0|84,050|0|
|5a|84,491|84,486|0|84,486|0|
|5c|198,004|197,997|0|197,997|0|

記録版2コミット `c214728b24` / `972c5f6d3c` の `panda.h` は同じblob `1c5e4a55049909f592fa14c262984b2039f4d1ca` で、returned offsetは128、rejected offsetは192。従ってsrc130は通常のbus130でも、bus2にいる別ECUからの通常受信でもなく、bus2に対応するreturned記録。

両版の `fdcan.h` も同じblob `8faa5a2810d709fc610063be8dcc15285d353402`。RXから転送先を決めて `can_send(..., bus_fwd_num, true)` に渡す処理があり、ホストsendcanに1D6がないことも合わせると、bus0で受信した純正1D6をPandaがbus2へ中継している構成と整合する。1CB・180にも同方向の記録がある。

この結果は[既存の接続経路の判断](leaf_transport_paths_20261105.md)を補強する。1D6の要求受信先が送信元と同じ車両側なら、Pandaの0→2転送を止めても車両側への純正要求を消せない。物理送信元、実際の受信先、bus0/1で共通量が見える理由はなお未確定。

### returnedも受理ACKではない

確認したfdcanドライバーは、送信フレームをTX FIFOへ書いてTXBARを設定した後でreturned記録を作る。その記録から、受信ECUが指令として受け入れた、実際に制動した、ホストが制御権を取得したとはいえない。Pandaフラッシュ済みバイナリの一致を今回測定したわけでもない。

1C3/2B0は3走行とも通常RXがbus1だけに記録され、各ホストsendcanは0。受信パターンを生成しているコードを今回追加・有効化した事実はない。

## 再現

[audit_raw_signals.py](../audit_raw_signals.py)で[監査JSON](../evidence/leaf_raw_signals_20261105.json)を生成した。入力は復旧原ログから作った9列形式のNPZ。全フレームの照合数、カウンター差分、returnedを含む受信チャネル、SHA256を保存する。

```sh
.venv/bin/python -m openpilot.tools.leaf_research.audit_raw_signals \
  /path/to/reextracted/00000059--02589b1b20.npz \
  /path/to/reextracted/0000005a--34bc682d3e.npz \
  /path/to/reextracted/0000005c--6a84234ad4.npz \
  --out /tmp/leaf-raw-signals.json
```

これで受信符号化と中継方向の追加照合は完了した。次に残るのは物理送受信ECU・受理/解除条件・実応答候補の区別であり、符号化一致だけでこれらを解決したとは扱わない。
