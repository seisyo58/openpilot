# 診断経路の再監査：bus1の75D識別は未確認

2026-11-04。資料購入・車両接続・送信・試験予約・comma変更は実施していない。

## 新しく整理できた点

保存済み生rlog6本（64/66/67/68/69/6a）を、707/727/75D/77D/1C3/2B0について全セグメント横断で数えた。各ファイルのハッシュ、bus別件数、診断payloadとsendcan一覧はleaf_diagnostic_bus_visibility.jsonに保存した。

- 75Dを試した5本（66/67/68/69/6a）のsendcanは合計28フレームで全てbus0。75Dへのbus1 sendcanは0。
- 77Dの応答はそれぞれbus0とbus2に6/5/7/3/7件。bus1の77Dは0。
- 75D要求の物理受信記録はbus2、送信エコーはbus128に見える。bus0へのsendcan自体をbus0の通常受信件数へ加えない。
- 一方、707は各ルートの起動照会でbus1から14フレーム送信され、727のbus1応答が10フレームある。6aの応答には自車既知FW6WK6ADBの21 83識別が含まれる。
- 1C3/2B0の通常受信は監査した6本で全てbus1。bus0/2での対象フレーム受信は0。

したがって「75D/bus0で拒否された」と「目的CANと同じbus1で75Dへ直接問い合わせても同じ」は、まだ同じ観測ではない。bus1上の75Dを一度も照会していないため、77Dが見えないことだけでbus1には存在しないとは言えない。

## この結果から言えないこと

- bus0の拒否応答をゲートウェイが作ったと断定できない。
- bus0が間違い、bus1が正解と断定できない。
- 同じ75Dが両busで同じ物理ECUへ到達するとは限らない。
- bus1で識別できても、そのECUが1C3/2B0の送信元であるとは確定しない。
- 診断への到達性とCommunicationControl対応、制御信号置換の受理は別問題。

ローカルPandaの共通転送処理は0↔2で、bus1を同じように転送しない。通常受信0/2の重複を別ECUや車両ゲートウェイ通過の証拠として数えない。これはチェックアウト上の実装であり、実機フラッシュのバイナリハッシュを今回確認したわけではない。起動FW照会設定にはbus0・bus1の複数経路があるが、登録済み宛先への照会であり、75Dが自動的に全経路で照会済みとは扱えない。

## 拒否応答の意味を再確認

AUTOSAR SWS_Dcm_00197はサービス不対応でNRC11、SWS_Dcm_00211は現在セッションで不許可のときNRC7F、SWS_Dcm_00217はSecurityAccess不足でNRC33を定める。自車の7F 28 11は標準的な意味ではサービス不対応であり、「同じ経路でセッション番号を変え続ける」「認証を試す」「引数だけ変える」を優先する根拠にはならない。ただし自車の準拠やゲートウェイの応答生成有無は未確認。

## 次の限定候補

追加実機試験を設計するなら、bus1・75Dへ既に自車bus0で成功した22 F1 88を一度だけ読み、同じbus1の77Dを待つ候補がある。新しいサービス／宛先総当たりではなく、既知の固定識別を別の観測経路で比較するもの。

- セッション変更、通信停止、再開、リセット、書込み、作動要求を含めない。
- bus1は非多重化状態を確認し、試験側と通常起動側の診断所有を排他的にする。通常運転中に別sendcan配信者を追加しない。
- F188要求1回、正しい新鮮なISO-TP First Frameに対するFCを最大1回。無応答・否定・不正形式なら終了し、別busへ自動再送しない。
- bus0/1/2を記録し、応答のbus、内容、対象CANの継続を監査する。
- bus1でも284E76WK2Eなら到達可能経路が増えたという結果。別識別なら同一対象と扱わず、無応答なら今回条件では識別できなかったという結果。
- どの結果でも、その場で通信停止へ進まない。従来の停止・F186手順の無効化は維持する。

今回この候補の実機コード変更・配備・予約は行っていない。以前のbus0固定識別試験の宛先busを単純に書き換えるだけでは、受信・FC・所有権・許可判定が一致しないため、そのまま実行しない。
