# 配分前の減速・制動要求CANの追加調査

調査日：2026-11-03。受信済みログと公開資料のみを使用し、車両へは送信していない。

## 結論

**回生と摩擦に分ける前の制動要求は、リーフのe-Pedalシステム内に存在する。対応するCAN IDは未確定だが、今回のログではBus 0の `0x1D6` が有力な候補になった。**

日産技報No.82（2018年3月）、印刷ページ31の「新型日産リーフのe-Pedalシステム」には、VCMがアクセル操作から目標制動トルクを求めてEDIBへ要求し、EDIBが回生と摩擦へ配分する構成が説明されている。ただし、この資料は当該要求のCAN ID・符号化・外部からの受理条件を示していない。

出典：[日産技報No.82、p.31「2. システム構成」・図2](https://www.nissan-global.com/JP/TECHNICALREVIEW/PDF/NISSAN_TECHINICAL_REVIEW_82.pdf)。

したがって、回生と摩擦の配分をopenpilot側で必ず実装しなければならない、とは現段階ではいえない。一方、「この信号を置き換えれば車側に配分を任せられる」と確認したわけでもない。

## 解析対象と方法

- 詳細ログ：`0abcc72a352961a0/00000059--02589b1b20`、全15区間。ユーザー申告ではe-Pedal使用。
- 比較：同じ走行内の手動運転とACC作動。別走行 `00000058--eb41dfe7a2` のqlogも補助的に参照。
- 受信Bus 0・1・2にある90組の周期的なメッセージ／バスの組み合わせ（5,000フレーム以上）を対象に、複数のビット位置・幅・符号・バイト順で変化と時間差を探索した。これは未解読信号の候補探索であり、あらゆる符号化を網羅したものではない。
- 実測加速度、ACC状態、運転者のペダル操作、`0x1C3`、`0x1CB`との対応を確認。
- e-Pedal ON/OFFそのものの状態ビットはまだ同定していない。

## 有力候補：Bus 0 / 0x1D6

0始まりのバイト番号で、先頭2バイトを符号なしビッグエンディアンとして読んだ。

```text
first_word = (byte[0] << 8) | byte[1]
candidate_delta = 12000 - first_word
```

`candidate_delta` は観察用の差分であり、Nmやm/s²へ校正した値ではない。

### 観測した特徴

1. 手動運転中には先頭ワードが12000から下がり、`candidate_delta` が増える。
2. それに対応して、ブレーキ協調側の `0x1CB` の第2の11ビット値が変わる。
3. 手動運転・車速2 m/s超・ブレーキペダル非操作という条件で、先頭ワードが11980未満の10,724サンプルを比較すると、`candidate_delta` と約20 ms後の `0x1CB` 第2値の相関は約0.9997。
4. 同じ条件のACC作動中では、42,842フレーム中42,824フレームが12000。ACC制動中にもほぼ変わらない。
5. 先に指定された比較ルートのqlogでは、Bus 0の `0x1D6` を37フレーム観測し、先頭ワードはすべて12000だった。ただし、間引かれた少数サンプルなので補助的な所見にとどまる。

この挙動は、e-Pedal側の制動要求経路という仮説と整合する。日産が説明する「VCMからEDIBへの配分前要求」の候補として優先して調べる価値がある。

ただし、受信ログだけでは送信元・受信先を確定できない。同じ量の再送、制限値、内部計算結果等の可能性も残る。時間差や相関だけで、指令入力であると断定しない。

## ACC側の制動：0x2B0と0x1C3

今回のACCの強い制動では、次の挙動だった。

- `0x2B0` は特別値2518に固定される。
- その間も `0x1C3` の値は連続的に増減する。
- `0x1CB` の値も、その後に変わる。
- 約424–429秒の制動部分では、`0x1CB` 第2値は `0x1C3` に対して約40 ms後に最もよく対応した。選んだ時間窓の波形相関は約0.9998。
- ほぼ停止中の約436–439秒では、`0x1CB` の第1値はゼロのまま、第2値は変動する。

`0x1CB` の観察用の読み取りは次のとおり。

```text
first11  = (byte[0] << 3) | (byte[1] >> 5)
second11 = (byte[2] << 3) | (byte[3] >> 5)
```

これらの位置は旧型Leafの公開定義と対応するが、今回のLeaf ICでの正確な単位・役割は未確定。特に第1値を回生要求、第2値を全制動力と呼ぶには追加の裏付けが必要。

**重要な修正：先の説明で `0x1C3` を「摩擦ブレーキ要求」と呼んだのは、StarPilot側の命名に基づく仮説であり、摩擦だけを要求する信号だと確定したわけではない。** EDIBへの全体的な制動要求や、その入力に相当する量である可能性を残す。日産のe-Pedalでの協調構成が、そのままACC入力にも適用されるかも未確認。

## 候補の整理

| 候補 | 今回の判断 |
|---|---|
| `0x1D6` 先頭ワード | e-Pedal側の配分前制動要求候補。ACC作動中はほぼ一定 |
| `0x1C3` | ACC側の可変制動要求候補。摩擦専用か、EDIB側で配分されるかは未確定 |
| `0x2B0` | 通常の駆動・減速要求候補だが、強い制動では特別値に固定。全域の減速要求を1つで表すとは確認できない |
| `0x1CB` | 制動協調に関係する候補。今回の時間差では上記要求の後に変化する例があり、上位入力と決めつけられない |
| `0x292`・`0x33D` | 実測・状態報告との区別がつかず、全体要求の候補として優先しない |

## 残っている確認事項

1. `0x1D6` の送信元がVCM、受信先がEDIBかを、該当年式の通信資料や非走行の配線・ベンチ環境で確かめる。
2. 先頭ワードと続く2バイトの役割、要求有効条件、停止保持、符号化と単位を特定する。
3. `0x1C3` を受けたEDIBが回生配分も行うかを、実際の回生量・油圧情報と対応させて検証する。今回はEV-CANの `0x1D4` / `0x1DA` を観測できておらず、実モータートルクによる配分の確認ができない。
4. 指令としての受理と制御引き継ぎは、信号の意味の同定とは別に確認する。
